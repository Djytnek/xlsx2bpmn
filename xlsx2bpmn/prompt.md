Прочитай описание процесса из файла `{{INPUT_MD}}`, составь по нему таблицу
и запиши её в файл `{{OUTPUT_TXT}}`.

## Формат файла

Файл должен содержать только таблицу. Никаких пояснений, заголовков,
markdown-разметки и знаков ```.

Ровно 9 колонок, разделитель — вертикальная черта `|`. Первая строка —
заголовок, скопируй её без изменений:

```
id|name|type|pool|lane|next|message_to|data_in|data_out
```

Главное правило формата: **в каждой строке ровно 8 вертикальных черт.**
Пустая ячейка — это две черты подряд: `||`. Если последние ячейки пустые,
черты всё равно нужны: строка заканчивается на `|||`.

Символ `|` нельзя использовать внутри названий. Пробелы вокруг черт допустимы.

## Главное правило: один pool, роли в lane

**pool — это организация, а не человек.** Обычно значение pool одно на всю
таблицу: название компании, чей процесс описан.

**lane — это роль или отдел внутри компании:** «Менеджер», «Бухгалтерия»,
«Склад», «Руководитель». Роли пиши в lane, а не в pool.

Отдельный pool заводится, только если участник **вне компании**: клиент,
поставщик, банк, налоговая. Их шаги нельзя связывать с внутренними через
next — для этого есть message_to (правило 7 ниже).

Если сомневаешься — оставь один pool. Так почти всегда правильно.

## Что писать в колонках

- **id** — короткий идентификатор латиницей: `t_check`, `gw_pay`, `doc_act`.
  Только латинские буквы, цифры и подчёркивание. Каждый id уникален.
- **name** — название шага по-русски, как в описании.
- **type** — из списка ниже, больше ничего.
- **pool** — организация. Обычно одно значение на всю таблицу.
- **lane** — роль или отдел, который делает шаг.
- **next** — что идёт следом, правила ниже.
- **message_to** — куда уходит сообщение в другой pool. Обычно пусто.
- **data_in** — документы, которые шаг читает. Обычно пусто.
- **data_out** — документы, которые шаг создаёт. Обычно пусто.

У строк с типом `dataObject` колонка lane всегда пустая: документ живёт
в пуле целиком, а не в отдельной дорожке.

## Допустимые значения type

Используй только эти девять:

| type | Когда |
|---|---|
| `startEvent` | начало процесса |
| `endEvent` | завершение процесса |
| `userTask` | шаг делает человек |
| `serviceTask` | шаг делает программа или система |
| `sendTask` | отправка письма, уведомления, документа |
| `receiveTask` | ожидание ответа или входящего документа |
| `exclusiveGateway` | развилка «или одно, или другое» |
| `parallelGateway` | развилка «и то, и другое одновременно» |
| `dataObject` | документ |

## Правила колонки next

- Один следующий шаг: `t_check`
- Несколько шагов сразу: `t_invoice; t_pack`
- Ветка с условием: `t_pay [Да] {сумма больше 1000}`
  — подпись в квадратных скобках, условие в фигурных
- Ветка по умолчанию: `*t_reject [Нет]`
  — звёздочка перед id, условия у неё нет
- У `endEvent` и у `dataObject` колонка next всегда пустая

Внутри next шаги разделяются точкой с запятой, а не чертой. Черта внутри
ячейки недопустима.

У `exclusiveGateway` должно быть минимум две ветки. У всех веток, кроме одной,
задай условие в фигурных скобках. Одну ветку пометь звёздочкой — это вариант
по умолчанию.

**Шаги в разных lane связываются обычным next.** Дорожки переходу не мешают.

## Обязательные правила

1. У каждого значения pool ровно один `startEvent` и хотя бы один `endEvent`.
2. Каждый шаг, кроме `endEvent` и `dataObject`, указан в колонке next
   ровно одного другого шага. Висячих шагов быть не должно.
3. Каждый id, упомянутый в next, существует в колонке id.
4. Документ объявляется отдельной строкой с type `dataObject`, и её pool
   совпадает с pool задач, которые с этим документом работают.
5. Документы в data_in и data_out перечисляются через `;`.
6. Ветки процесса обязательно приходят в `endEvent`. Если после развилки пути
   больше не пересекаются — у каждого свой `endEvent`.
7. Шаги разных pool нельзя связывать через next. Если работа переходит
   к внешнему участнику, у своего шага поставь `sendTask`, у чужого —
   `startEvent` или `receiveTask`, и свяжи их через колонку message_to.

## Пример 1: одна компания, роли в дорожках

Описание:

> ## Согласование отпуска
> Заявление поступает в отдел кадров. Кадровик проверяет остаток дней.
> Если дней хватает, руководитель согласует заявление, после чего кадровик
> вносит приказ. Если не хватает, сотруднику отправляют отказ.

Таблица:

```
id|name|type|pool|lane|next|message_to|data_in|data_out
hr_start|Заявление поступило|startEvent|ООО Ромашка|Отдел кадров|hr_check|||
hr_check|Проверить остаток дней|userTask|ООО Ромашка|Отдел кадров|gw_days||doc_app|
gw_days|Дней достаточно?|exclusiveGateway|ООО Ромашка|Отдел кадров|hr_approve [Да] {дней хватает}; *hr_reject [Нет]|||
hr_approve|Согласовать заявление|userTask|ООО Ромашка|Руководитель|hr_order||doc_app|
hr_order|Внести приказ|serviceTask|ООО Ромашка|Отдел кадров|e_ok|||doc_order
hr_reject|Отправить отказ|sendTask|ООО Ромашка|Отдел кадров|e_no|||doc_deny
e_ok|Отпуск оформлен|endEvent|ООО Ромашка|Отдел кадров||||
e_no|Заявление отклонено|endEvent|ООО Ромашка|Отдел кадров||||
doc_app|Заявление|dataObject|ООО Ромашка|||||
doc_order|Приказ|dataObject|ООО Ромашка|||||
doc_deny|Уведомление об отказе|dataObject|ООО Ромашка|||||
```

Обрати внимание: «Отдел кадров» и «Руководитель» — это дорожки одной
компании, и переход между ними идёт обычным next.

## Пример 2: появился внешний участник

Клиент — не сотрудник компании, поэтому он отдельный pool, и связь с ним
идёт через message_to. У каждого pool свои startEvent и endEvent.

Описание:

> ## Заказ товара
> Клиент отправляет заявку в магазин и ждёт ответа. Менеджер принимает
> заявку, склад проверяет наличие, менеджер отвечает клиенту.

Таблица:

```
id|name|type|pool|lane|next|message_to|data_in|data_out
c_start|Нужен товар|startEvent|Клиент||c_send|||
c_send|Отправить заявку|sendTask|Клиент||c_wait|s_start||
c_wait|Дождаться ответа|receiveTask|Клиент||c_end|||
c_end|Ответ получен|endEvent|Клиент|||||
s_start|Заявка получена|startEvent|ООО Ромашка|Менеджер|s_check|||
s_check|Проверить наличие|userTask|ООО Ромашка|Склад|s_reply|||
s_reply|Ответить клиенту|sendTask|ООО Ромашка|Менеджер|s_end|c_wait||
s_end|Заявка обработана|endEvent|ООО Ромашка|Менеджер||||
```

## Порядок работы

1. Определи компанию, чей это процесс — это значение pool для всех
   внутренних шагов.
2. Выпиши роли и отделы внутри компании — это значения lane.
3. Выпиши каждое действие из описания отдельной строкой.
4. Добавь `startEvent` в начало и `endEvent` в конец каждого pool.
5. Найди в тексте слова «если», «в случае», «иначе» — там нужен
   `exclusiveGateway`.
6. Найди слова «одновременно», «параллельно» — там `parallelGateway`.
7. Заполни next: у каждого шага пропиши, что идёт после него.
8. Если есть внешний участник — свяжи его через message_to.
9. Выпиши все документы отдельными строками `dataObject` и проставь data_in
   и data_out у задач.
10. Пересчитай черты в каждой строке.

## Проверь перед записью файла

- В каждой строке ровно 8 вертикальных черт.
- Внутри ячеек нет символа `|`.
- Роли записаны в lane, а не в pool.
- Все id уникальны и написаны латиницей.
- Каждый id из next есть в колонке id — сверь по одному.
- В каждом pool есть startEvent и endEvent.
- У каждого exclusiveGateway одна ветка помечена звёздочкой.
- У endEvent и dataObject колонка next пустая, у dataObject ещё и lane.
- В файле нет ничего, кроме таблицы.
