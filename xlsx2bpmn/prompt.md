Прочитай описание процесса из файла `{{INPUT_MD}}`, составь по нему таблицу
и запиши её в файл `{{OUTPUT_TXT}}`.

## Формат файла

Файл должен содержать только таблицу. Никаких пояснений, заголовков,
markdown-разметки и знаков ```.

Ровно 10 колонок, разделитель — вертикальная черта `|`. Первая строка —
заголовок, скопируй её без изменений:

```
id|name|type|pool|lane|parent_id|next|message_to|data_in|data_out
```

Главное правило формата: **в каждой строке ровно 9 вертикальных черт.**
Пустая ячейка — это две черты подряд: `||`. Если последние ячейки пустые,
черты всё равно нужны: строка заканчивается на `|||`.

Символ `|` нельзя использовать внутри названий. Пробелы вокруг черт допустимы.

## Главное правило: один pool, роли в lane

**pool — это организация, а не человек.** Обычно значение pool одно на всю
таблицу: название компании, чей процесс описан.

**lane — это роль или отдел внутри компании:** «Менеджер», «Бухгалтерия»,
«Склад», «Руководитель». Роли пиши в lane, а не в pool.

Отдельный pool заводится, только если участник **вне компании**: клиент,
поставщик, банк, налоговая. Их шаги нельзя связывать с внутренними через
next — для этого есть message_to (правило 7 ниже).

Если сомневаешься — оставь один pool. Так почти всегда правильно.

**Название компании бери из описания процесса.** В примерах ниже названия
разные и выдуманы для примеров — переносить их в свою таблицу нельзя.
Если в описании компания не названа ни разу, напиши в pool слово
`Организация`, но ничего не придумывай и не бери из примеров.

## Что писать в колонках

- **id** — короткий идентификатор латиницей: `t_check`, `gw_pay`, `doc_act`.
  Только латинские буквы, цифры и подчёркивание. Каждый id уникален.
- **name** — название шага по-русски, как в описании.
- **type** — из списка ниже, больше ничего.
- **pool** — организация. Обычно одно значение на всю таблицу.
- **lane** — роль или отдел, который делает шаг.
- **parent_id** — id подпроцесса, внутри которого лежит шаг. Обычно пусто,
  см. раздел про подпроцессы.
- **next** — что идёт следом, правила ниже.
- **message_to** — куда уходит сообщение в другой pool. Обычно пусто.
- **data_in** — документы, которые шаг читает. Обычно пусто.
- **data_out** — документы, которые шаг создаёт. Обычно пусто.

У строк с типом `dataObject` колонки lane и parent_id всегда пустые: документ
живёт в пуле целиком, а не в отдельной дорожке.

## Допустимые значения type

Используй только эти десять:

| type | Когда |
|---|---|
| `startEvent` | начало процесса |
| `endEvent` | завершение процесса |
| `userTask` | шаг делает человек |
| `serviceTask` | шаг делает программа или система |
| `sendTask` | отправка письма, уведомления, документа |
| `receiveTask` | ожидание ответа или входящего документа |
| `exclusiveGateway` | развилка «или одно, или другое» |
| `parallelGateway` | развилка «и то, и другое одновременно» |
| `subProcess` | шаг, внутри которого спрятана своя последовательность |
| `dataObject` | документ |

## Правила колонки next

- Один следующий шаг: `t_check`
- Несколько шагов сразу: `t_invoice; t_pack`
- Ветка с условием: `t_pay [Да] {сумма больше 1000}`
  — подпись в квадратных скобках, условие в фигурных
- Ветка по умолчанию: `*t_reject [Нет]`
  — звёздочка перед id, условия у неё нет
- У `endEvent` и у `dataObject` колонка next всегда пустая

Внутри next шаги разделяются точкой с запятой, а не чертой. Черта внутри
ячейки недопустима.

У `exclusiveGateway` должно быть минимум две ветки. У всех веток, кроме одной,
задай условие в фигурных скобках. Одну ветку пометь звёздочкой — это вариант
по умолчанию.

**Шаги в разных lane связываются обычным next.** Дорожки переходу не мешают.

## Подпроцессы

Подпроцесс — шаг, внутри которого спрятана своя последовательность действий.
На верхнем уровне видно один прямоугольник «Проверка поставщика», а внутри
у него свои шаги. Это важная часть: большой процесс, выписанный одной длинной
цепочкой, читать невозможно.

**Когда заводить.** Если в описании про один шаг сказано, из чего он состоит,
или встречаются слова «процедура», «в порядке, установленном», «включает
в себя», «проводится в несколько этапов» — это подпроцесс. Как правило,
подпроцесс оправдан, когда внутри набирается три шага и больше.

Не увлекайся: два-четыре подпроцесса на процесс — обычное дело, десять — нет.

**Как записывать.** Две части:

1. **Сам подпроцесс** — обычная строка с type `subProcess` на верхнем уровне.
   У неё заполнены pool и lane, parent_id пустой, а в next стоит то, что
   идёт после подпроцесса целиком.
2. **Его содержимое** — строки, у которых в parent_id стоит id этого
   подпроцесса. У них **lane всегда пустой**, а pool тот же самый.

**Четыре правила содержимого:**

- у каждого подпроцесса есть **свой** `startEvent` и **свой** `endEvent`;
- next внутри подпроцесса ведёт только к строкам этого же подпроцесса;
- ни одна строка снаружи не ссылается на строки внутри;
- подпроцесс можно вложить в подпроцесс: у него самого тоже будет parent_id.

## Обязательные правила

1. У каждого значения pool ровно один `startEvent` и хотя бы один `endEvent`.
   Внутри каждого подпроцесса — тоже свои.
2. Каждый шаг, кроме `startEvent`, `endEvent` и `dataObject`, указан в колонке
   next ровно одного другого шага. Висячих шагов быть не должно.
3. Каждый id, упомянутый в next, существует в колонке id.
4. Документ объявляется отдельной строкой с type `dataObject`, и её pool
   совпадает с pool задач, которые с этим документом работают.
5. Документы в data_in и data_out перечисляются через `;`.
6. Ветки процесса обязательно приходят в `endEvent`. Если после развилки пути
   больше не пересекаются — у каждого свой `endEvent`.
7. Шаги разных pool нельзя связывать через next. Если работа переходит
   к внешнему участнику, у своего шага поставь `sendTask`, у чужого —
   `startEvent` или `receiveTask`, и свяжи их через колонку message_to.

## Пример 1: одна компания, роли в дорожках

Описание:

> ## Согласование отпуска в ООО «Северный ветер»
> Заявление поступает в отдел кадров. Кадровик проверяет остаток дней.
> Если дней хватает, руководитель согласует заявление, после чего кадровик
> вносит приказ. Если не хватает, сотруднику отправляют отказ.

Таблица:

```
id|name|type|pool|lane|parent_id|next|message_to|data_in|data_out
hr_start|Заявление поступило|startEvent|ООО «Северный ветер»|Отдел кадров||hr_check|||
hr_check|Проверить остаток дней|userTask|ООО «Северный ветер»|Отдел кадров||gw_days||doc_app|
gw_days|Дней достаточно?|exclusiveGateway|ООО «Северный ветер»|Отдел кадров||hr_approve [Да] {дней хватает}; *hr_reject [Нет]|||
hr_approve|Согласовать заявление|userTask|ООО «Северный ветер»|Руководитель||hr_order||doc_app|
hr_order|Внести приказ|serviceTask|ООО «Северный ветер»|Отдел кадров||e_ok|||doc_order
hr_reject|Отправить отказ|sendTask|ООО «Северный ветер»|Отдел кадров||e_no|||doc_deny
e_ok|Отпуск оформлен|endEvent|ООО «Северный ветер»|Отдел кадров|||||
e_no|Заявление отклонено|endEvent|ООО «Северный ветер»|Отдел кадров|||||
doc_app|Заявление|dataObject|ООО «Северный ветер»||||||
doc_order|Приказ|dataObject|ООО «Северный ветер»||||||
doc_deny|Уведомление об отказе|dataObject|ООО «Северный ветер»||||||
```

Обрати внимание: «Отдел кадров» и «Руководитель» — это дорожки одной
компании, и переход между ними идёт обычным next.

## Пример 2: подпроцесс

Описание:

> ## Закупка в АО «Мостстрой»
> Заявка поступает в отдел снабжения, снабженец её оформляет. Дальше юрист
> проводит проверку поставщика: запрашивает документы, проверяет их
> и выносит заключение. После проверки снабженец проводит закупку.

Таблица:

```
id|name|type|pool|lane|parent_id|next|message_to|data_in|data_out
s|Заявка получена|startEvent|АО «Мостстрой»|Снабжение||t_form|||
t_form|Оформить заявку|userTask|АО «Мостстрой»|Снабжение||sub_check|||
sub_check|Проверка поставщика|subProcess|АО «Мостстрой»|Юрист||t_buy|||
c_s|Начали проверку|startEvent|АО «Мостстрой»||sub_check|c_ask|||
c_ask|Запросить документы|userTask|АО «Мостстрой»||sub_check|c_look|||
c_look|Проверить документы|userTask|АО «Мостстрой»||sub_check|c_e||doc_set|
c_e|Проверка завершена|endEvent|АО «Мостстрой»||sub_check||||
t_buy|Провести закупку|userTask|АО «Мостстрой»|Снабжение||e|||
e|Закупка проведена|endEvent|АО «Мостстрой»|Снабжение|||||
doc_set|Пакет документов поставщика|dataObject|АО «Мостстрой»||||||
```

Строка `sub_check` стоит на верхнем уровне: у неё есть lane и next. Четыре
строки под ней — её содержимое: parent_id заполнен, lane пуст, внутри свои
начало и конец.

## Пример 3: появился внешний участник

Клиент — не сотрудник компании, поэтому он отдельный pool, и связь с ним
идёт через message_to. У каждого pool свои startEvent и endEvent.

Описание:

> ## Заказ товара
> Клиент отправляет заявку в магазин «Три кита» и ждёт ответа. Менеджер принимает
> заявку, склад проверяет наличие, менеджер отвечает клиенту.

Таблица:

```
id|name|type|pool|lane|parent_id|next|message_to|data_in|data_out
c_start|Нужен товар|startEvent|Клиент|||c_send|||
c_send|Отправить заявку|sendTask|Клиент|||c_wait|s_start||
c_wait|Дождаться ответа|receiveTask|Клиент|||c_end|||
c_end|Ответ получен|endEvent|Клиент||||||
s_start|Заявка получена|startEvent|магазин «Три кита»|Менеджер||s_check|||
s_check|Проверить наличие|userTask|магазин «Три кита»|Склад||s_reply|||
s_reply|Ответить клиенту|sendTask|магазин «Три кита»|Менеджер||s_end|c_wait||
s_end|Заявка обработана|endEvent|магазин «Три кита»|Менеджер|||||
```

## Порядок работы

1. Определи компанию, чей это процесс — это значение pool для всех
   внутренних шагов.
2. Выпиши роли и отделы внутри компании — это значения lane.
3. Выпиши каждое действие из описания отдельной строкой.
4. Посмотри, где описание раскрывает один шаг через несколько других —
   там заведи `subProcess` и перенеси эти шаги внутрь через parent_id.
5. Добавь `startEvent` в начало и `endEvent` в конец каждого pool
   и каждого подпроцесса.
6. Найди в тексте слова «если», «в случае», «иначе» — там нужен
   `exclusiveGateway`.
7. Найди слова «одновременно», «параллельно» — там `parallelGateway`.
8. Заполни next: у каждого шага пропиши, что идёт после него.
9. Если есть внешний участник — свяжи его через message_to.
10. Выпиши все документы отдельными строками `dataObject` и проставь data_in
    и data_out у задач.
11. Пересчитай черты в каждой строке.

## Проверь перед записью файла

- В каждой строке ровно 9 вертикальных черт.
- Внутри ячеек нет символа `|`.
- Роли записаны в lane, а не в pool.
- Название компании в pool взято из описания процесса, а не из примеров
  этого промпта.
- Все id уникальны и написаны латиницей.
- Каждый id из next есть в колонке id — сверь по одному.
- В каждом pool есть startEvent и endEvent.
- У каждого подпроцесса есть свои startEvent и endEvent.
- Ни один next не ведёт из подпроцесса наружу или снаружи внутрь.
- У строк с заполненным parent_id колонка lane пустая.
- У каждого exclusiveGateway одна ветка помечена звёздочкой.
- У endEvent и dataObject колонка next пустая, у dataObject ещё lane
  и parent_id.
- В файле нет ничего, кроме таблицы.
