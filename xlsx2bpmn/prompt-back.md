Прочитай таблицу процесса из файла `{{INPUT_TXT}}`, изложи её человеческим
текстом и запиши результат в файл `{{OUTPUT_MD}}`.

Это обратная задача: не по описанию собрать таблицу, а по таблице написать
описание, которое можно показать людям, приложить к регламенту или отдать
на согласование.

## Как устроена таблица

Колонки разделены вертикальной чертой `|`, первая строка — заголовок.
Колонок может быть меньше, чем в примере: пустые в файл не попадают.

```
id|name|type|pool|lane|parent_id|next|message_to|data_in|data_out
```

- **id** — служебное имя строки. **В описание не попадает никогда.**
- **name** — название шага, его и пиши.
- **type** — что это за шаг:

| type | Как понимать |
|---|---|
| `startEvent` | процесс начинается |
| `endEvent` | процесс заканчивается |
| `userTask` | шаг делает человек |
| `serviceTask` | шаг делает программа или система |
| `sendTask` | что-то отправляют наружу |
| `receiveTask` | чего-то ждут извне |
| `exclusiveGateway` | развилка: пойдёт или туда, или сюда |
| `parallelGateway` | ветки идут одновременно |
| `subProcess` | шаг, у которого внутри своя последовательность |
| `dataObject` | документ, а не действие |

- **pool** — организация. Несколько значений — значит участников несколько.
- **lane** — роль или отдел, который делает шаг.
- **parent_id** — если заполнен, шаг лежит внутри подпроцесса с таким id.
- **next** — что идёт следом. `t_pay [Да] {сумма больше 1000}` читается как
  «если сумма больше 1000 — переходим к шагу t_pay, ветка называется „Да“».
  Звёздочка `*t_reject` — ветка «во всех остальных случаях».
- **message_to** — шаг отправляет сообщение другому участнику.
- **data_in** — шаг использует документ, **data_out** — создаёт документ.

## Каким должно быть описание

Обычный русский текст, как в регламенте. Никаких таблиц, никаких `id`,
никаких английских слов вроде `userTask` и `exclusiveGateway`.

Порядок изложения — **по ходу процесса**, а не по порядку строк в файле.
Начни со `startEvent` и иди по колонке next.

Строй так:

```markdown
# Название процесса

## Участники
Кто задействован: организации и роли внутри них.

## Ход процесса
1. Шаг за шагом, по порядку. У каждого шага сказано, кто его делает.
2. ...

## Развилки
Где процесс расходится и по какому условию.

## Документы
Какие документы появляются и на каком шаге.
```

Разделы, для которых в таблице ничего нет, просто не пиши: нет документов —
нет раздела «Документы».

## Правила

1. **Ничего не выдумывай.** В описании может быть только то, что есть
   в таблице. Не додумывай сроки, ответственных, причины и последствия.
2. **Не потеряй ни одной строки.** Каждый шаг таблицы должен быть упомянут.
   Строки `dataObject` — в разделе про документы.
3. **Кто делает — обязательно.** Для каждого шага назови роль из lane,
   а если участников несколько — и организацию из pool.
4. **Развилки словами.** `gw [Да] {сумма больше 1000}; *gw2 [Нет]` — это
   «если сумма больше 1000 — …, иначе — …». Название ветки и условие оба
   идут в текст.
5. **Подпроцессы — отдельным разделом.** Шаг с type `subProcess` в основном
   ходе назови одной строкой, а его содержимое вынеси вниз:

   ```markdown
   ## Проверка поставщика
   Что происходит внутри этого шага:
   1. ...
   ```

   Содержимое — это строки, у которых parent_id равен id подпроцесса.
   Вложенный подпроцесс — свой подраздел внутри.
6. **Служебные id не показывай.** Ни в тексте, ни в скобках. Человек,
   читающий описание, про них знать не должен.
7. **Параллельные ветки** (`parallelGateway`) описывай как «одновременно
   начинаются …», а не как последовательность.
8. **Сообщения между организациями** (message_to) описывай как передачу:
   «менеджер отвечает клиенту».

## Пример

Таблица:

```
id|name|type|pool|lane|parent_id|next|data_in|data_out
hr_start|Заявление поступило|startEvent|ООО Ромашка|Отдел кадров||hr_check||
hr_check|Проверить остаток дней|userTask|ООО Ромашка|Отдел кадров||gw_days|doc_app|
gw_days|Дней достаточно?|exclusiveGateway|ООО Ромашка|Отдел кадров||hr_approve [Да] {дней хватает}; *hr_reject [Нет]||
hr_approve|Согласовать заявление|userTask|ООО Ромашка|Руководитель||hr_order|doc_app|
hr_order|Внести приказ|serviceTask|ООО Ромашка|Отдел кадров||e_ok||doc_order
hr_reject|Отправить отказ|sendTask|ООО Ромашка|Отдел кадров||e_no||doc_deny
e_ok|Отпуск оформлен|endEvent|ООО Ромашка|Отдел кадров||||
e_no|Заявление отклонено|endEvent|ООО Ромашка|Отдел кадров||||
doc_app|Заявление|dataObject|ООО Ромашка|||||
doc_order|Приказ|dataObject|ООО Ромашка|||||
doc_deny|Уведомление об отказе|dataObject|ООО Ромашка|||||
```

Описание:

```markdown
# Согласование отпуска

## Участники
Процесс идёт внутри ООО «Ромашка». Задействованы две роли: отдел кадров
и руководитель.

## Ход процесса
1. Процесс начинается с поступления заявления.
2. Отдел кадров проверяет остаток дней, опираясь на заявление.
3. Дальше всё зависит от того, хватает ли дней.
4. Если дней хватает, руководитель согласует заявление, а затем система
   вносит приказ. На этом отпуск оформлен.
5. Если дней не хватает, отдел кадров отправляет сотруднику отказ.
   Заявление считается отклонённым.

## Развилки
После проверки остатка дней процесс расходится: при достаточном остатке
идёт согласование у руководителя, во всех остальных случаях — отказ.

## Документы
- **Заявление** — используется при проверке остатка дней и при согласовании.
- **Приказ** — появляется на шаге внесения приказа.
- **Уведомление об отказе** — появляется при отправке отказа.
```

## Проверь перед записью файла

- Каждая строка таблицы отражена в тексте.
- Ни одного `id` в описании нет.
- У каждого шага сказано, кто его делает.
- Оба исхода каждой развилки описаны.
- Содержимое каждого подпроцесса вынесено своим разделом.
- В тексте нет ничего, чего нет в таблице.
